# 文档生命周期政策

本文是 OPL 文档生命周期的唯一政策 owner。

## 一份文档，一个职责

每份文档必须能用一句话说明唯一职责。判断依据是读者要完成的任务和内容的决策职责；不能仅凭标题词汇或篇幅判定是否拆分。禁止在同一篇文档中混合现态说明、未来目标、历史流水、兼容说明或临时的排障日记。

| 文档 / 目录 | 唯一职责 |
| --- | --- |
| `docs/README.md` | 本仓文档导航入口，只映射阅读路径，不定义业务规则 |
| `docs/project.md` | 产品定位、分层边界与 Package 拓扑晋升条件 |
| `docs/architecture.md` | 静态结构、依赖方向、物理归属与运行控制链 |
| `docs/invariants.md` | 实现与演进不得破坏的硬约束 |
| `docs/decisions.md` | 当前仍有效、且无法仅从代码读出的关键取舍 |
| `docs/status.md` | 当前已实现能力摘要、验证边界与动态 readback 入口 |
| `docs/active/` | 唯一 active gap owner（仅限有具体断点、owner 与验收条件的未完成项） |
| `docs/policies/` | 跨实现长期生效的治理原则（不含流水或清单） |
| `docs/specs/` | 稳定的人读接口规范与跨 owner 行为合同 |
| `docs/runtime/` | 运行时对象、服务托管与调度边界 |
| `docs/delivery/` | 交付物、Package 载荷与发布边界 |
| `docs/references/` | 不决定状态或架构的非权威维护参考 |

## 生命周期

1. **创建**：只有现有 owner 无法清楚承载一个长期独立职责时才新建文档。
2. **维护**：修改语义时更新唯一 owner，且**按段落/条目级别**逐条核对现役源码、合同与真实 caller；其他文档只链接，不复制正文，也不得在无关文档末尾顺手外挂补丁段落。
3. **收敛与整合**：发现重复时把仍有效内容合入唯一 owner 后删除重复文档；遇到按日期、版本号、Issue/PR 或逐项功能堆叠的长清单时，必须按理想目标态重写整合为结构化规则，动态成员、数量与版本一律交回 `contracts/` 与 CLI readback。
4. **完成**：active gap 完成后直接删除条目；active 文档没有完成区。
5. **退役（零兼容面）**：先从当前源码、合同和真实 consumer 证明替代路径与切换，再直接删除文档中的旧模块、旧接口、旧脚本、兼容叙事、示例以及仅保护旧行为的测试。不得在活跃文档保留 `docs/history/` 墓碑页、redirect、退役接口黑名单或“为旧安装暂留兼容”的说明。仍保护身份、权限、数据完整性或真实调用的检查不得随文案误删。
6. **追溯**：历史使用 Git commit、blame、tag、release artifact。删除前将仍影响未来决策的理由、否定保证和恢复条件归入当前主题 owner；未完成提案不得当作已完成历史抹去。

来源、法律依据或恢复所需的原始材料，以及现役合同通过路径或哈希引用的原始产物和收据，
按其证据职责以不可变 Git commit URL 或独立机器数据路径绑定，不混充日常操作或架构文档；
不能把旧提案重新变成待办或把旧脚本重新列为当前命令。仅有“历史”或“冻结”标签不构成保留依据，
自写完成叙事仍应归入 Git；变更原始证据前须核对真实引用和完整性绑定。

## 禁止的内容形态

- 按日期、版本、PR/Issue 或轮次持续追加的决策、完成记录或审计流水；
- 在既有人读文档末尾外挂与主题无关的补丁记录或迁移说明；
- 固定运行计数、version、receipt、workflow run、branch 或 worktree；
- 同时描述 current、target、migration 和 history 的大而全文件；
- 已完成 plan 继续放在 `active/` 或保留 `docs/history/` 墓碑目录；
- 用旧接口名称解释“它已经退役”或宣称保留兼容入口；
- 为每个品牌、Package、场景或 Agent 复制同一套状态和成熟度模板；
- 用 Markdown 关键词、标题、段落或行数作为语义测试。

## 机器检查边界

允许机器检查：

- Markdown 相对链接和资源存在；
- front matter、schema、JSON 和 generated artifact 完整性；
- 可执行命令示例；
- secrets、权限和不可逆动作边界；
- source/generated provenance。

机器不得通过固定措辞、关键词、章节、文件数量或文本快照决定产品语义、架构、状态、优先级或完成度。语义由当前 owner 基于 contracts、源码、caller 和真实 readback 判断。

## 修改文档时

1. 先确认主题 owner 和当前代码事实。
2. 对相关段落分类为 current truth、active gap、support detail 或 stale。
3. 把 current truth 留在唯一 owner；active gap 只进入唯一 gap 文档；独特 support detail 放入明确专题。
4. 删除 stale、重复、历史和兼容叙事。
5. 更新所有链接和 machine ref。
6. 运行链接、结构和受影响 contract/test 验证。

文档变更不能单独证明 runtime、installed、release、domain 或 product readiness。

## 跨仓分工与复核触发

每个仓维护自己的文档导航和职责；Framework 不复制 App、Cloud、Flow 或领域仓的实现状态。
跨仓文档通过 owner 仓的稳定入口和 machine contract 连接。多语言文档是同一语义的翻译，
生成页面是源文档的投影，两者都不形成独立 owner。

各仓可以保留一份本文的应用说明，用来承载本仓独有的目录职责和保留条件；它必须标明本文是
规则 owner，不复制本文正文，也不定义第二套家族级生命周期规则。

API/caller 切换、模块删除、默认配置变化、安装路径变化、提案落地或白皮书源变化时，
在同一修改中检查直接引用、导航、可执行示例和生成入口。检查生成物是否依赖被删除源；
通过原生成器更新它，不能手工修补投影，也不能把本地构建称为公开发布。

索引只解释阅读路径；架构只解释结构；政策只定义约束；操作手册只指导操作；
状态只说明实现证据；gap 必须有具体断点、负责人和验收方式。常驻职责不作为未完成任务，
已完成 Issue 的过程不回填状态页。专题可以保留必要上下文，但详细规则只在一个位置维护。

每次交付回读受影响文件和链接，运行对应仓库现有机械检查；没有现成检查时可用有界链接审计。
不建立关键词门禁、强制章节模板、第二进度表或自动语义评分器。
