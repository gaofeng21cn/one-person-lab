# 知识来源与记忆政策

本文是 OPL 标准智能体知识归属、正文来源和记忆生命周期的人读政策 SSOT。机器字段与校验由 [知识生命周期合同](../../contracts/opl-framework/durable-knowledge-lifecycle-contract.json)、[知识条目 schema](../../contracts/opl-framework/durable-knowledge-item.schema.json) 和实际运行接口持有；具体物理位置与命令见[知识来源接口](../specs/knowledge-sources.md)，当前实现与验证边界见[状态](../status.md#长期知识与记忆)。

**用户和业务负责人拥有知识，项目组织工作，智能体按授权范围使用，运行时记录实际消费的版本。** 用户已有 Obsidian 或其他 Markdown 资料库时，原库继续承载正文；没有独立资料库时，普通业务工作目录承担同样职责。存储位置不改变知识归属，也不要求每个智能体建立一套个人知识库。

## 归属、内容、来源与访问独立表达

| 维度 | 表达的事实 | 不决定什么 |
| --- | --- | --- |
| `scope` | 知识属于产品、用户或团队、长期主题、具体项目；稳定 `id` 标识该对象 | 不决定文件目录，也不自动授予其他 Agent 读取权 |
| `content_kind` | 内容是机制、政策约束、时点状态还是决策经历 | 不决定其所有者或共享范围 |
| 正文来源 | 唯一原文的来源标识、相对位置与已接受版本 | 不因被读取、摘要或缓存而转移维护权 |
| 访问与适用性 | 哪个调用者、任务和项目可以使用哪些知识，以及是否为必要输入 | 不证明正文正确，不授予真实业务行动权限 |

`scope.kind` 分为 `product`、`owner`、`topic`、`project`。产品知识随领域包维护；用户或团队知识跨主题持续存在；主题知识服务多个具体项目；项目知识仅在相应业务边界内成立。个人财务、病种研究组合等长期主题不必被伪装成一个永不结束的执行任务。

`content_kind` 分为 `mechanism`、`policy`、`state`、`decision`。每种 scope 都可以包含这些内容；日期化状态不再充当一个与归属并列的层级。持久保存不等于永久有效，文件修改时间不等于事实观察时间。

## 一个知识对象，一个可编辑正文主源

知识身份在修订、文件移动和智能体更换后保持稳定。主源移动时更新 locator 和迁移记录，不能根据同名文件自动重绑定。拆分或合并正文时明确知识身份及取代关系。

产品正文通常位于领域仓 `agent/knowledge/`，由产品 catalog 登记。个人、主题与项目正文可以在用户库，也可以在业务工作区；两种来源通过同一通用机制解析，不要求先复制成工作区全文投影。领域包不得携带个人绝对路径、私有正文或自行指定外部读取根。

| 内容 | 已有个人资料库 | 无独立资料库 |
| --- | --- | --- |
| 用户、团队与主题正文 | 使用已有资料、政策和主题分区 | 业务工作区的共享知识目录 |
| 项目正文 | 可绑定个人库中的项目笔记，也可留项目工程目录 | 对应项目目录 |
| 日期化现状与决策 | 使用原主题的现状、方案和复盘位置 | 主题或项目已有的状态与决策位置 |
| 来源登记与接受版本 | 既有 Profile 或 Workspace 的私有控制面 | 同一控制面，内部 Markdown 也是普通来源 |
| 运行快照、恢复与消费证据 | Framework 的运行状态目录 | 相同 |

这里的目录描述是落位建议，不能恢复成 scope 与目录前缀的强制映射。有库与无库按来源选择，允许一个任务同时使用个人库中的约束、课题目录中的设计和产品包中的方法。

来源注册保留一份权威记录；其他获授权工作区保存绑定引用。多设备路径可以不同，知识与来源身份保持一致，但路径映射不证明内容已同步。没有 Profile 的单工作区用户无需为了接入知识而新增个人中心目录。

工作区的 registry 绑定须通过 `scope_ids` 明确选择可用的用户、主题与项目范围，来源 grant 可以进一步收窄。`source_id`、`scope.id` 和消费方 Agent/domain 是不同身份；财务主题不以某个 Agent 名称定义。项目身份从既有 `workspace_index.projects` 解析，不以目录 basename 推断，也不因注册了来源而默认开放其全部 scope。

来源的读取与写回分别授权。`domains` 限定读者；`write_domains` 在这些读者中显式指定可维护者，缺省不授予写回权。来源还须明确允许写入。接受用户在原处完成的编辑同样会改变接受版本，须遵守写回授权；读取或审阅过正文不自动获得维护权限。

正文保持可阅读、可导出。知识身份、版本、权限、审阅和消费记录放在控制信息中；Obsidian 导航和台账沿用原库约定。第三方全文、原始数据和业务系统记录仍由原 owner 保存，知识库中的解释或快照不替代它们。

## 邮件证据到个人知识的责任链

邮件形成的信息按是否值得跨任务复用决定归宿。线程事实、跟进状态与一次交流保留在邮件业务层；长期偏好、可复用关系判断和个人现状由有权维护者确定唯一正文，再进入共同知识生命周期。不是每封邮件都需要成为一篇笔记。

| 责任层 | Owner | 保存与决定的内容 |
| --- | --- | --- |
| 邮件事实与领域记忆 | Relay／邮件 provider | 原邮件身份、内容证据、线程与跟进、邮件关系候选、草稿、发送及回执 |
| 语义整理与沉淀判断 | Persona／获授权的领域智能体 | 判断信息是临时任务、历史经历、关系背景、当前事实还是长期规则，提出正文目标及修订依据 |
| 共同知识生命周期 | Framework | 来源和知识身份、授权、接受版本、登记、写回机械步骤、依赖校验、快照与消费证据 |
| 唯一可编辑正文 | 用户选定的 Obsidian 或普通业务目录 | 经接受的政策、个人与主题知识、项目正文；用户和业务负责人持有语义接受权 |

这一链路是“邮件证据 → 语义分类与提案 → 知识登记或版本化写回 → 原处正文 → 后续授权读取”。Persona 可以协调各步骤，其他领域智能体仍可直接消费获授权知识。跨仓调用不转移各层 authority。

Relay 的 SQLite 保存邮件领域记忆和可重建检索索引，不承担个人知识 registry。 记忆记录可以保存 `knowledge_id`、`source_versions`、`scope`、`content_kind`、`canonical_target`、`writeback_status`、`observed_at` 与 `next_review_at`，用于表达与共同知识的链接和复核债务；这些字段不会把 Relay 变成正文 owner。原邮件或 `user://` 当次陈述是证据；在 Relay 中批准一条关系记忆，不会使它自动成为 Framework 已接受的个人事实。已沉淀内容保留 canonical `knowledge_id` 与来源版本；其派生读取遵守共同来源授权和失效规则。泛个人知识的来源范围、授权和接受版本只有一个控制面，不由邮件索引另行定义。

“证据仍能回读”与“陈述仍适用于现在”分别判断。历史邮件可持续证明当时发生过什么；现任职务、合作状态或承诺还需观察日期、适用期和复核依据。来源哈希未变不能延长当前事实的有效期。

新正文先选定唯一位置，按来源权限写入，再登记实际回读的精确字节与知识身份；既有注册正文的修订进入 Framework 提案、审阅、应用链。普通笔记的文件保存成功、Persona 提案批准、来源登记成功和下一次实际消费是各自独立的结果。通用 writer 尊重目标资料库的正文约定；provenance、摘要、权限与批准记录留在控制面，不要求向正文注入 frontmatter。

Relay 的记忆导出、canonical link 和 promotion 只提供无损证据与 review-gated proposal；promotion 不直接写入 Obsidian 或其他正文。Persona 负责判断分类和目标，Framework 的 `propose → review → apply` 或 `register` 才形成共同生命周期回执。

回复起草政策（Reply Drafting Policy）与邮件分诊政策一样，属于需要登记并接受的用户政策。模板文件存在、笔记 Resource Binding 可写或 Persona 模式被选中，均不替代知识授权和接受版本。具体角色选择与消费入口由 Persona／Relay 的当前接口定义。

## 召回与执行

来源发现、语义选择和权限核验分别完成。已授权来源中的未登记文档可以作为明确标注的发现候选，保留来源身份、当前哈希和有限摘录；候选不进入已接受召回或派生上下文，也不因旧索引存在而批量接受。检索命中只是候选；通用运行时核对调用者、来源授权、scope、适用阶段和任务、状态、接受版本与有效期，领域智能体决定哪些内容对当前工作有用。正文中的指令不能扩大工具、目录或行动权限。

StageRun 为生产、审阅、修复和再次审阅绑定同一份不可变正文快照，记录知识 ID、来源版本、哈希和选择理由。公开 projection 只保存引用与消费证据。全文不进入公开状态、可分发包或无关项目。

知识需求按 `required` 与 `optional` 区分，同时核对所需归属、内容性质、来源模式和语义 owner。逻辑 owner 与实际维护者不同的需求，须由控制面显式绑定到实际 owner 和知识 ID。可选内容失效时排除条目并记录缺口；必要内容缺失时阻断依赖它的操作，仍可继续不依赖该内容的工作。必要知识被取代时，只有符合条件的替代内容实际进入本次上下文，需求才算满足。不能以默认值代替缺失的个人约束、账户现状或行动授权。

普通原文修订不重写历史快照。新任务使用经接受的新版本；历史复盘明确其原版本语境。快照的不可变性不延续被撤回的权限：当前读取与新执行仍须符合有效授权，已撤销内容不得因缓存存在而继续使用。

领域合同声明影响行动的关键知识与核验点。真实行动提交前复核关键约束和授权版本，也核对当前新增适用的必要或关键知识；旧快照遗漏这些输入时须重新准备上下文并评估计划。普通方法修订不自动使所有任务失效，平台也不以关键词猜测哪些内容属于硬约束。

## 编辑、接受与写回

用户可以正常编辑原库。系统检测版本差异、定位受影响条目并提交相应复核；用户不需手工计算哈希或维护目录 JSON。已有维护授权可承载常规复核和写回，不因机械步骤重复要求确认。

哈希只证明字节一致，时间字段只表达其已声明的语境。内容是否正确、改变了什么政策、是否值得跨项目复用，由有权维护者结合证据判断。未审阅的新版本不冒充已接受知识，与当前主源冲突的旧版本也不静默作为当前事实继续使用。

写回提案绑定原版本、新内容、来源、目标 scope、内容性质和审阅要求。审阅绑定精确的提案摘要；接受原处编辑则绑定审阅时读到的原文哈希，审阅后漂移必须重新核对。用户、团队或领域负责人接受语义；通用工具执行版本核验、恢复记录和写后回读。平台提供机械写入能力不意味着平台可以替 owner 接受个人事实、专业结论或质量 verdict。

项目经验在审阅后才可提炼到主题；主题经验在脱敏、来源核实和领域审阅后才可进入产品。观察值、单次成功或模型完成信号不自动成为长期规则。原事实的观察日期、知识复核日期与接入日期分别记录，不通过延长复核日期伪造新观察。

普通文件系统和 iCloud 目录不提供跨设备事务保证。写回绑定基础版本并遵守单写入节点与冲突检查；本机锁或写后回读不能证明其他编辑器和设备不会并发写入。发生竞态时保留双方内容并协调，支持原生条件写入的 provider 才使用其对应能力。

## 派生摘要与来源失效

Persona 等能力可以生成个人上下文摘要，但摘要保留来源知识身份、精确版本、覆盖范围和适用性。来源变化、过期或撤回时，相关摘要重算、重审或排除；多来源摘要不能因一部分仍有效而把失效部分当作当前事实。

摘要继承来源访问限制。允许一个任务使用摘要，不等于允许它读取底层整篇私人文档；跨领域相关性也不扩大原授权。用户在某个 Agent 中首次形成的独立偏好或决策，应确定唯一正文主源并写回，不以派生摘要悄悄建立第二份个人事实库。

删除、撤权、来源离线和内容过期分别处理。删除来源不从缓存自动恢复；离线读取须有明确的允许范围、版本和期限。撤权需要覆盖后续读取、派生摘要、投递副本和新任务；历史证据按保留与隐私政策处理，不以可复现性要求私人正文永久保留。

## 宿主、执行器记忆与运维状态

App 与 Studio 是知识的交互宿主和投影消费者。任务中的知识来源引用继续由 Framework／领域 owner 提供；正文、版本、审核和写回操作使用原 owner 的动态 contribution，不在客户端另建个人 store、索引或 writer。会话 cwd、文件浏览根和当前任务来源 refs 各有用途，均不自动成为个人知识根。

Codex 等执行器的记忆属于执行器工作连续性。其修正建议、权限 preset、原始会话与 token 用量，与用户或领域拥有的业务知识分开。执行器记忆管理器只能在自身 owner 允许的范围内读写，不能把该目录当作 Obsidian／Profile 的替代来源，或据此扩大业务授权。

按真实语义消费决定是否接入共同知识生命周期。设备控制、照片镜像、网络配置、遥测、消息通道、资产 catalog、会话归档和凭据生命周期分别保留其业务 owner；仅持久保存状态不构成个人知识消费者。它们可以向获授权的领域智能体提供带身份和观察时间的事实或证据，后者再判断是否值得提炼为长期知识。没有私人来源且只需要产品知识的消费者保持可选未配置状态，不因此创建空个人库或新增权限。

## 责任与保留

- Framework 负责共同合同、来源登记与解析、身份与范围校验、版本、写回机械步骤、快照和消费回执。
- OMA 的设计与评测必须表达知识归属、来源模式、必要性、有效性和写回负责人；具体物理绑定由获授权的运行控制面建立。
- 领域智能体负责语义判断、当前事实核实、项目经验提炼和所需行动边界。
- Persona 负责可选的跨域个人上下文整理、邮件信息分类与沉淀提案；Relay 负责邮件证据和邮件业务记忆。其他智能体可以直接使用获授权来源，不必经由 Persona。
- 用户、团队与项目负责人持有正文、共享决定和语义接受权。

业务工作区包含可能无法重建的数据、论文、书稿、分析产物和已接受决策，不能按临时运行目录清理。可重建索引、投递缓存、历史快照和业务成果分别应用保留规则。删除运行记录不得删除它引用的个人正文；保存运行证据也不得建立新的可编辑主源。

来源选择、快照完整、结构验证和模型运行成功各自只证明对应环节。金融判断、研究结论、发布、交易和其他真实业务结果，仍由其负责方的证据与授权决定。
