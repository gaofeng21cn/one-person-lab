# 第三方贡献准入政策

本文持有 `gaofeng21cn` 自行维护仓库的贡献准入原则。各仓库的 `AGENTS.md`、贡献指南及自动化入口引用本文，产品目标与合同仍由对应仓库持有。具体账号身份、合作关系和仓库范围属于私有维护信息，由受信维护环境中的协作登记表提供，不写入公开仓库。上游镜像和归档仓库不因此恢复维护。

## 先判身份，再判改动

| 档位 | 适用范围 | Agent 处理原则 |
| --- | --- | --- |
| 本人及自用账号 | 维护者明确确认的本人或自用账号 | 无条件信任其产品意图，直接进入合并流程；不要求另开 Issue、证明必要性或接受第三方提案审查，不另设主观审批。 |
| 指定仓库合作开发者 | 维护者明确登记、且与目标仓库精确匹配的合作账号 | 以信任为主，按最新 SSOT 核对目标与实际改动，采用与风险相称的验证；不机械套用第三方 Issue 前置条件。有具体冲突时修正或拆分，不照单全收。 |
| 第三方开发者 | 其他账号，以及合作账号在登记范围以外的贡献 | 以审慎质疑为起点；按实际 diff、目标仓库产品设计理念与最新 SSOT 独立评估；对原 PR 谨慎把关，发现背后真实问题有价值时以自主收敛推进为主，且每项判断均须公开回复提出者。 |

身份按 GitHub 不变数字 ID 与目标仓库核对，但具体登记不公开。登录名只用于可读展示；写权限、历史合并、`COLLABORATOR`/`MEMBER` 标签或待审 PR 自己修改的名单都不能升级信任等级。合作范围不跨仓继承；新增账号或扩大范围须由维护者明确确认。

维护自动化从调用方指定的私有协作登记读取当前可信版本，并在私有审计中保留版本依据。登记完整、读取成功且没有匹配项时按第三方处理；登记不可读、过期或冲突时为身份未知，先核实，继续不依赖该身份判断的工作。公开回复只解释提案的事实、证据缺口与产品适配，不披露内部身份关系、信任判断或退出原因。

信任档位决定提案审查方式，不授予 GitHub 权限，也不绕过真实分支保护、冲突处理、既有确定性检查或身份、权限和数据完整性边界。本人账号直接合并，不意味着替该 PR 自动发布、部署或操作生产资源。

## 贡献分类

对第三方 PR，维护者按实际 diff 和最新 SSOT 判断性质，再决定是否需要补充 Issue：

- **Debug**：修复现有合同和原始意图已经明确的错误，且维护者能在当前主线的相关受支持环境中容易复现、明确判断。修复应恢复预期行为，不夹带新的产品选择、限制或能力。提交者不喜欢的产品设计不是 Bug。
- **未复现 Debug**：报告看起来像 Bug，但当前主线无法复现，也没有足够证据锁定根因。它不能按已证 Bug 直接合并。
- **行为改造**：改变现有用户行为、默认值、限制、权限、兼容范围、数据语义或 owner 边界，即使改动被描述为“修复”“对齐”或“兼容”。
- **新增功能**：增加此前不存在的能力、入口、模型、平台、适配器、工作流或 UI。

## 准入条件

可复现 Debug 的 PR 不强制配套 Issue，维护者可直接修复或评估合并。PR 应给出复现步骤、受影响版本或环境、实际结果与预期结果，以及修复范围和验证方式。维护者复现后核对根因，验证修复恢复原有意图且没有附带行为变更；不因能复现就照单接受整个 PR。

未复现 Debug、行为改造和新增功能必须关联配套 Issue，建议在编写实现前提交。Issue 说明用户要完成什么、当前实际与预期行为、为什么有必要处理，以及日志、截图、最小示例、测试、调用链或其他可核对凭证。涉及行为改造时，还须说明原始意图或 SSOT 依据、默认与显式 opt-in 路径的变化、兼容和权限影响；迁移或不可逆影响须说明恢复方式。无需为了填表虚构不适用的内容。

有关联 Issue 只是进入评估的条件，不代表认可方案。已有同问题的有效 Issue 可以复用，无需重复新建。一个 PR 同时包含 Bug 修复和行为改造或新增功能时，须拆分，或为后两者提供相应 Issue 与证据；可复现的 Bug 不授权夹带其他改动。

第三方改变行为或增加核心能力时，必要性必须由提交者在 Issue 中证明，包括具体用户问题、与最新 SSOT 的关系、可核对凭证及影响。标题、标签或正文称“修复”“兼容”“对齐”，仍按实际行为差异分类。第三方 PR 不能只通过修改 contract、增加测试或通过 CI 来证明必要性。

评估任何非纯 Debug 的行为改造或新增功能前，须先读取目标仓库的产品定位、核心设计理念、架构/合同与非目标边界（如 `README.md`、`AGENTS.md`、`docs/architecture.md` 及对应合同），明确判断该诉求是恢复既有理念、顺应理念的低风险增量，还是会改写产品设计、抬高默认路径复杂度或增加维护耦合。可选扩展原则上置于显式、默认关闭配置之后，并分别验证默认路径与启用路径。

同时将 **“这个 PR 本身是否可直接合并”** 与 **“它背后的用户问题是否值得处理”** 分开判断：不盲目合入缺证据、越界或方案失当的 PR，也不承担替作者编造理由吸收不当方案的义务；但在处置前应主动独立甄别其点出的真实痛点——若问题真实存在、契合产品设计理念且边界清晰风险可控，应在现有授权内以自主推进闭环为主（在最小边界内修正收敛、给出接替实现，或纳入既有 Issue 跟踪），避免因作者未按模板自证完美而一刀切丢弃有价值的线索；若诉求明显违背设计理念或缺乏可核对依据，则自主拒绝并关闭；仅当真正改变核心产品定位、涉及不可逆/受保护/外部契约取舍或重大设计路线分歧等非常必要场景下，才提请维护者人工决策，尽量减少人工介入。

## 证据不足与各档处置时的公开回复要求

所有做出处置判断的 Issue 与 PR（包括直接合并、调整/接替落地、拆分、要求补充最小证据、转入后续跟踪或拒绝关闭），都必须沿用提出者使用的语言在原条目上给出具体、尊重、有事实与产品设计理念依据的公开回复，并在写后回读确认。回复中不得披露内部身份关系、私人信任档位或内部判断过程。

以下情况可直接关闭原 PR，并在公开回复中说明具体缺口、设计理念适配判断以及重新提交或跟踪路径：

- 声称是 Debug，但维护者无法复现，且没有配套 Issue 或 Issue 未提供足够的现象、必要性和凭证；
- PR 改造或新增能力，却没有关联 Issue 且不满足以最小接替方式自主收敛的条件；
- Issue 只是占位链接，没有足够的用户任务、必要性、凭证或相关影响说明；
- 变更会影响默认行为、权限或安全边界，但没有独立的必要性和回归证据。

关闭前须读完讨论、检索同类已处理案例、主动识别背后问题是否值得另有承接，回复贡献者的实际关切并写明缺少哪些事实或重提条件；回复后回读并确认 PR 已关闭。维护者自身的读取、认证、配额或工具故障不等于贡献者证据不足，不能据此关闭。

## 模板要求

GitHub Issue 与 PR 模板只收集上述判断所需事实，不以关键词、篇幅或自动勾选代替维护者的语义判断。维护者仍须读完整讨论、核对当前主线和真实调用链，再决定修复、拆分、补证据、关闭或合并。
