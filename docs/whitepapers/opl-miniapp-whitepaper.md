# OPL Agent Apps：Agent 原生应用与 MiniApp 白皮书

> 让智能体直接完成工作，让人在需要判断与协作时自然进入

适用对象：希望开发、使用或集成 Agent 原生应用的用户、开发者与技术决策者。

核心判断：Agent 原生应用应让智能体通过稳定能力直接推进工作，让人与智能体在同一事实和操作边界内协作，并复用用户已经拥有的连接与知识。

## 应用从工作目标开始

传统应用通常要求用户先打开窗口、寻找页面、填入信息，再逐步完成操作。智能体改变了这条路径：用户可以直接表达目标，由 Agent 查找资料、调用能力、形成成果，并在需要专业判断或个人选择时邀请用户参与。

这种变化要求应用重新安排自己的核心。业务能力必须能够被 Agent 清楚发现和可靠调用，界面则应围绕具体工作出现。用户审阅一封邮件、比较几种方案、标注视频片段或修改一项决定时，可以直接进入相关内容；完成后，Agent 能理解发生了什么，并沿着同一项工作继续。

OPL 将这套共通理念称为 **OPL Agent Apps（OPL Agent 原生应用）**。它适用于标准智能体、其他 Agent、个人工作流和各类 App：以可调用的领域能力和可持续的工作状态为核心，在人需要参与时提供协作界面。后台自动化与专业桌面应用都可以遵循这一理念，是否拥有窗口、是否采用标准智能体运行方式，由具体工作决定。

**OPL MiniApp** 是其中按需出现的协作 UI。它把当前工作所需的状态、材料、选择与操作呈现在一个可由 Agent 打开的界面中，让双方围绕同一个对象协作。MiniApp 可以很小，也可以承载专业编辑器；大小由工作需要决定。没有人机交互需求的能力，同样能够通过共用基座参与 Agent 原生工作。

## 同一项工作，两个参与者

Agent 和人使用应用的方式不同。Agent 需要明确的输入、结果、错误和后续动作；人需要可理解的布局、可比较的证据和直接操作的反馈。两种入口应连接到同一个业务负责方，并共享任务、产物与版本身份。

例如，Agent 准备回复一封邮件时，先读取邮件负责方提供的原信与收件人信息，形成草稿。用户打开 MiniApp 后看到这份草稿和来源，可以改写正文、调整收件人或保存。Agent 随后读取更新后的真实草稿，继续处理用户的意见。发送仍由邮件负责方执行，沿用其业务确认要求。界面中的保存提示、Agent 的叙述和实际发送结果各有明确含义。

这种协作要求应用把“看见”“选择”“编辑”“提交”表达清楚。选择一段证据，可以更新 Agent 的上下文；把文字放入输入框，只形成待发送内容；启动工作和执行外部操作则通过对应的正式入口。界面打开本身应当是观察动作，不能为了展示结果再次执行已经完成的操作。

人和 Agent 还可能同时修改内容。应用需要在实际负责方核对版本，在冲突时保留双方修改并请求合适的处理。收到超时或未知执行结果时，应先查询真实状态，再决定能否重试。这样，人机协作才能在网络变化、页面刷新和会话切换之后继续成立。

## 用适合工作的界面

OPL Agent Apps 按工作需要选择呈现方式。共享视图与专用 MCP App 提供会话中的 MiniApp 协作，专业应用则承载需要持续操作的工作面，三者可以相互衔接。

| 呈现方式 | 适合的工作 | 复用重点 |
| --- | --- | --- |
| 共享声明式视图 | 任务进度、成果列表、证据详情、方案比较与确认 | 使用统一视图组件，领域负责方提供数据与可用操作 |
| 专用 MCP App | 邮件编辑、媒体审看、复杂领域交互 | 使用标准宿主协议，保留专业布局和编辑行为 |
| 专业应用 | 持续创作、设备控制、空间探索与实时监测 | 保留原生工作面，通过稳定入口衔接任务和成果 |

选择界面的依据，是它能否让用户更准确、更省力地完成当前工作。纯自动化能力可以只提供机器入口；没有需要人处理的信息时，无需额外展示页面。已有成熟专业界面的应用，也可以保留自己的工作面，由 Agent 定位对象并在操作后读取结果。

共享视图按内容能力选择组件，例如进度、产物、审阅或活动记录。新的领域能力只需声明已有组件可以理解的数据，即可获得基本协作体验。只有交互确实具有独特性时，才增加专用界面。这样既避免每个 Agent 重写列表、空态和确认框，也允许专业工作保持必要的表达能力。

## 复用标准，保持自由组合

MiniMax Code MiniApp 展示了一个有价值的方向：Agent 负责推进工作，人通过专业工作台完成审阅、编辑与确认，双方复用业务服务。其插件清单、运行上下文和客户端桥接属于 MiniMax 宿主的实现约定。OPL 借鉴这一协作方式，并以自己的既有产品边界承接。[MiniMax Code MiniApps 官方项目](https://github.com/MiniMax-AI/MiniMax-Code-MiniApps)

OPL 的会话内界面采用标准 MCP Apps，使工具结果与交互资源能够通过支持该规范的宿主协作。Package 继续作为安装单元；Framework 负责能力发现、工作运行与共享投影；Studio 通过 DSH、Cordis 和官方 MCP Apps SDK 提供宿主适配；领域 Package 维护业务能力与专业判断。[MCP Apps 官方文档](https://modelcontextprotocol.io/docs/extensions/apps)

因此，OPL Agent Apps 定义整体开发与协作方式，MiniApp 提供其中需要的交互界面。它们沿用现有 Package、MCP、插件生命周期与权限机制，开发者可以直接复用既有安装身份、通用通信协议和能力发现入口。

宿主能力不同，体验也应有清楚的降级路径。支持 MCP Apps 的宿主呈现交互界面；其他调用方仍能获得结构化结果，并在适用时使用由负责方提供的专业应用或浏览器入口。业务执行不能依赖某个页面恰好保持打开。

## 连接一次，按任务使用

用户希望新应用快速可用，最直接的条件是能够复用已有连接。已经连接的邮箱、文件服务或设备，不应因为安装了新的 MiniApp 就要求用户重新录入全部信息。

OPL Connect 统一连接引用、能力授权与连接修复。凭证的存储、刷新和账户生命周期继续由相应服务提供方或原生载体负责。应用获得的是获准调用某项能力的通路，长期凭证不会成为传入界面或 Agent 上下文的普通数据。

授权对象必须来自可信宿主核实的已安装能力。页面上选中了某个 Package，只表示导航焦点；它不能据此冒充这个 Package 申请或执行操作。每次调用还需要检查连接和授权是否仍然有效，撤销或连接变化应能及时影响后续使用。

共享连接也需要保留业务含义。允许读取邮件，不等于允许发送；允许查看资料，不等于允许覆盖原文。应用使用已有授权推进可完成的工作，只在真正缺少权限或存在必须由用户决定的事项时提出请求。统一连接由此减少重复配置，同时保持每项操作的范围清楚。[连接与授权说明](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/specs/connection-authorization.md)

## 用户拥有知识，应用按需理解

Agent 原生应用应当能够使用用户已经积累的通用信息。语言与表达偏好、长期约束、团队规则和主题知识，都可能服务于多个应用。每个应用重新询问、各存一份，最终会形成相互矛盾的个人资料。

OPL 的知识基座以归属组织内容。产品知识描述可分发的方法与规则；用户或团队知识描述跨工作共享的信息；主题知识服务于持续的生活或专业事务；项目知识记录某项具体工作的决定与经验。四类归属与存储位置分开，也与内容的时效性分开。

长期方法、当前事实和历史决策可以出现在任何一类归属中。个人投资原则可以长期使用，账户状态则需要标明观察日期；研究方法可以跨课题复用，某个课题的设计选择只适用于相应项目。系统应根据来源、适用范围和有效期决定是否使用，避免把一份旧事实当成永久背景。

用户已有 Obsidian 或其他 Markdown 资料库时，知识正文可以保留在原处。工作区登记获准使用的来源与范围，并为每次运行冻结实际使用的版本。没有个人资料库时，普通工作目录也能承担相同职责。用户无需为了使用 OPL 再维护一套独立的个人知识中心。

运行快照保存的是当次依据，供执行、审阅和复查使用；日常修改仍回到知识主源。Agent 产生新的认识后，应明确它属于哪个用户、主题或项目，形成可审阅的修订，并在确认当前原文版本后写回原处。来源变更、过期或撤回时，相关摘要也需要重审或失效。

Persona 可以帮助整理跨领域背景和来源摘要，但各应用可以通过获准的知识来源完成工作，不必把全部读取集中到 Persona。检索与摘要同样只是获取上下文的方法，不能改变原始知识的归属。

“Agent 已经知道”意味着它能在当前任务范围内取得合适的上下文，并说明依据。它不意味着整库内容应默认进入每次会话，也不意味着知道某项偏好便获得执行外部操作的许可。真正便捷的体验来自准确复用，而不是无差别复制。

## 让工作在界面之外持续

很多专业工作需要数分钟、数小时甚至更长时间。MiniApp 应能显示已经完成的部分，让用户在后续阶段仍能查看、比较和利用中间成果。进度表达执行到了哪里，质量意见表达成果还有什么问题，两者分别呈现。

长任务由既有运行负责方管理，并返回稳定的工作身份。关闭窗口、刷新页面或切换宿主后，重新打开同一项工作，应继续观察原有运行。真正的暂停、恢复或取消都通过负责方公开的操作完成。

在一个研究任务中，Agent 可以持续整理证据，用户进入 MiniApp 查看研究路径、失败尝试和待决定事项。用户选择补充材料或调整目标后，系统将决定交给实际负责方；页面不会因为一条进度完成就代替领域审阅宣布结论成立。

这也使不同应用能够围绕同一份成果协作。研究 Agent 形成材料，写作能力继续加工，审阅界面呈现修改意见；每次交接都保留准确的成果引用与版本，而非依赖用户复制聊天文本来重建工作。

## 共享基座提高开发质量下限

新应用的开发应先回答：它完成什么工作，谁拥有真实状态，哪些操作可由 Agent 调用，在哪些环节人需要参与。确定这些问题后，再选择共享视图、专用 MCP App 或专业应用作为呈现方式。

共同机制应集中复用。能力发现、上下文传递、连接授权、知识来源、长任务观察、产物引用、主题与语言适配，都有现有负责方。领域开发者把精力放在输入与结果的语义、专业判断、真实业务操作和必要交互上。

Framework 维护通用基座的源码、合同与标准。标准智能体、其他 Agent 和 App 通过安装的 Framework 及其公开模块、命令行与服务接口复用这些能力；各领域仓继续维护自己的业务逻辑。源码维护位置与实际安装位置可以不同，宿主沿各自的安装和升级路径选择可用基座。

共用机制也保留数据的原有归属。私人运行状态由相应运行负责方管理，知识来源的授权与绑定留在私有控制范围，Obsidian 或普通资料目录中的正文仍由用户维护，邮件、照片和其他领域数据继续由原业务负责方保存。基座连接这些来源并记录必要的运行依据；具体分工见[共用基座的物理归属](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/architecture.md#共用基座的物理归属)。

一套可复用基座还需要可执行的开发样例。样例应展示最小业务能力如何同时被 Agent 和 UI 使用，如何继承获准上下文，如何处理缺少信息、冲突和未知结果，以及如何在不支持界面的环境中继续工作。新应用在同一条最小工作链上完成验收，再扩展自己的专业能力。

质量下限由实际行为证明：Agent 能找到并调用能力；UI 呈现同一份真实结果；用户修改不会被旧请求覆盖；关闭后可以继续原任务；失效授权无法继续使用；知识更新能影响后续运行；专业成果能够追溯到负责方。协议测试、界面验收、安装验证和领域质量评估分别提供相应证据。

共享机制的边界也应随真实复用形成。重复出现且稳定的能力适合进入基座；只属于一个领域的规则继续留在该领域。这样，OPL Agent Apps 可以减少重复造轮子，同时保持每个应用独立理解、演进和交付的能力。

## 让新增能力自然进入已有工作

OPL Agent Apps 的价值最终体现在一次普通使用中：用户表达目标，Agent 找到合适能力，沿用获准的连接和知识，准备可以审阅的成果；用户在必要的环节通过 MiniApp 或专业应用参与，完成判断后，Agent 继续推进并回读真实结果。

随着应用增加，用户积累的是可复用的工作方式、知识和成果。开发者积累的是可靠的领域能力与共享组件。每个新应用都能从已有基础开始，并通过同一套协作要求证明自己的可用性。

共同要求由 [OPL Agent 原生应用标准](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/policies/agent-native-app-policy.md) 维护，接入步骤见[开发指南](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/mcp-apps/development.md)；产品体验由 [One Person Lab App](https://github.com/gaofeng21cn/one-person-lab-app) 负责。各应用按自身工作特点接入这套标准，统一的是人、Agent 与真实工作之间的关系。
